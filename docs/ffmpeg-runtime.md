# Bundled local FFmpeg runtime

Accepted runtime decision (2026-10-01): bundled browser **FFmpeg 5.1.4 is authoritative** for supported local media inspection, preview, and final processing. Native FFmpeg is optional diagnostics/developer tooling; browser processing has no native 9.0.2 minimum. See [the ADR](../_bmad-output/planning-artifacts/architecture/ADR-2026-10-01-local-runtime.md).

The browser workers load the checked-in core from `/ffmpeg/`; they do not contact a CDN. The generated core is built by `scripts/ffmpeg-wasm/Dockerfile` using Emscripten 3.1.40, FFmpeg n5.1.4, and ffmpeg.wasm commit `f876f907c7e9b9bf51d4ed0b913a855a63ae63fc`. MP3 encoding uses LAME 3.100 from the `ffmpegwasm/lame` mirror pinned to `2badea1974ae36cb8312afe99cff1e6b3b5decee`, built as a static library with the shared library and frontend disabled. Build output includes FFmpeg, binding, and LAME source archives and licenses under `public/ffmpeg/source/`. Rebuild with Docker Buildx using that Dockerfile and export the artifact stage to `public/ffmpeg`.

The expanded recipe disables all features before explicitly enabling WAV, MP3, FLAC, MOV/MP4, and Matroska demuxers; PCM, MP3, AAC, FLAC, ALAC, Opus, and Vorbis audio decoders; file/pipe protocols; and WAV, raw-float, FLAC, MP3, ipod (M4A), MOV, MP4, Matroska, and streamhash muxers. Encoders are floating-point/24-bit PCM, native FLAC/AAC, and `libmp3lame`; MP3 output targets 192 kbps and enhanced video audio targets AAC 192 kbps. The recipe enables `aac_adtstoasc` and `h264_mp4toannexb` bitstream filters and links the LAME library. Network support is disabled, and no GPL or nonfree option is enabled. The earlier baseline configure summary reported LGPL 2.1-or-later. These are build observations, not licensing certification. Review notices, corresponding sources, build materials, and added encoder libraries for the actual distribution; no compliance promise is made here.

The architecture's native 9.0.2 cold-start seed is superseded for browser processing by the accepted ADR. The implemented capability detector reports **Browser FFmpeg** Ready only when both local core files match the SHA-256 hashes in `public/ffmpeg/runtime-manifest.json`, whose version is pinned to 5.1.4. Missing, invalid, or mismatched files/manifest report Unavailable. Browser execution is checked when processing starts; file integrity alone does not prove execution on every browser. **Native FFmpeg (optional)** is a separate diagnostic: missing native tooling is Limited and does not block browser readiness. Experimental model-manifest availability is also separate from production qualification and successful inference.

After every core rebuild, export the generated JS/WASM and accompanying sources/licenses, calculate SHA-256 over the exact exported file bytes, and regenerate both entries in `public/ffmpeg/runtime-manifest.json` as lowercase 64-character hex hashes. On Windows, use `Get-FileHash public/ffmpeg/ffmpeg-core.js, public/ffmpeg/ffmpeg-core.wasm -Algorithm SHA256` to obtain the hashes. Keep the manifest version aligned with the actual FFmpeg build; changing the pinned version also requires updating detector validation and verification evidence. Run `npm run verify:ffmpeg` and the scoped capability tests before distributing the rebuilt files and manifest together. A stale manifest makes the browser runtime Unavailable; update it only for an intentional, verified rebuild.

`.gitattributes` marks `public/ffmpeg/ffmpeg-core.js` and `public/ffmpeg/ffmpeg-core.wasm` as `-text`. These rules disable Git text/line-ending conversion for the generated assets, preserving their exact hashed bytes across checkout even with `core.autocrlf` enabled. Retain the rules and avoid formatting or normalizing generated core files. Verify the checkout hashes against the manifest if integrity diagnostics fail; do not replace trusted hashes merely to accept unexpectedly altered files.

Build and core verification status (2026-10-01): recorded results show the expanded core build and `npm run verify:ffmpeg` **passed**. Generated runtime assets and FFmpeg/binding/LAME source archives and licenses, including `lame-LICENSE`, accompany the bundle. The verifier executes the bundled WASM core in a Node.js harness; this result is not a native system-FFmpeg compatibility claim. The inspected verifier covers the following paths:

| Verified bundled-core path | Recorded result |
| --- | --- |
| WAV / PCM | Decode, range trim, resample, float WAV validation, and PCM24 WAV encoding passed |
| FLAC / native `flac` | Encode/decode roundtrip passed |
| MP3 / `libmp3lame` 192 kbps | Encode/decode roundtrip passed |
| M4A / native `aac` 192 kbps / `ipod` muxer | Encode/decode roundtrip passed |
| MOV, MKV, MP4 / copied video + AAC 192 kbps | Remux passed; source/output video-stream SHA-256 packet fingerprints were identical for each fixture |

These are recorded core-verifier results, not tests rerun in this documentation update. Audio roundtrips check decode and duration; they do not establish enhancement quality or bit-identical lossy audio. Fixture coverage does not establish every possible codec/container combination or the complete browser final-job flow.

The source-video output policy preserves all video packets plus metadata and chapters, and includes only the selected enhanced audio encoded as AAC. Unselected audio, subtitles, data streams, and attachments are explicitly omitted with UI disclosure. Video streams are copied without re-encoding; there is no H.264 re-encoding fallback. Unsupported remux must fail visibly rather than silently transcode. The streamhash checks passed for the MOV/MKV/MP4 fixtures above. Metadata/chapters, selected enhanced audio, and UI disclosure remain product requirements; this core-verifier result does not independently prove them. Seven-format decode/preview evidence remains separate from final-export evidence.

Use `npm run verify:ffmpeg` to reproduce the recorded core checks and the declared browser fixture checks for actual worker behavior. Browser acceptance must also check metadata/chapters, selected enhanced AAC and disclosed stream omissions, cancellation, cleanup, and final-artifact publication. No runtime or physical-platform test was run during this documentation update.

Production preview remains gated on a qualified model and a validated playable artifact for every enabled stage. For private local testing, the user has separately approved an explicitly **experimental** DPDFNet2 noise-removal preview even though DPDFNet2 has not passed the speech-quality gate. Unsupported enabled stages must fail visibly; they cannot be silently omitted. A successful experimental preview must come from actual model inference, be validated and retained locally for comparison, and stay labeled experimental. Decoded source PCM is always removed from the worker's virtual filesystem and must never be exposed as an enhanced result.
