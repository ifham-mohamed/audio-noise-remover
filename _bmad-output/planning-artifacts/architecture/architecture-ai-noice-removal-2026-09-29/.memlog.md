- (constraint) The application must support Windows, macOS, and Linux.
- (constraint) All media and processing must remain on the user's laptop; no cloud upload or external processing service is allowed.
- (constraint) The application must handle MP3, WAV, M4A, FLAC, MP4, MOV, and MKV according to the input media type.
- (decision) The first product scope is speech and voice recordings; music and mixed-audio support is a planned later extension.
- (decision) Noise removal and enhancement controls must be independently controllable, including voice clarity, loudness normalization, echo/reverb reduction, and preservation-oriented processing.
- (decision) The user interface must be a local web application opened in the user's browser.
- (assumption) Hardware capability will be detected at runtime and the processing pipeline will provide CPU-safe fallbacks, with optional GPU acceleration when available.
- (direction) The architecture should separate media demux/decode/encode, audio analysis, noise reduction, enhancement stages, job orchestration, and the browser UI so later music and mixed-audio support can be added without replacing the product shell.
- (decision) Use a local browser application with a Next.js App Router frontend written in TypeScript, styled with Tailwind CSS and shadcn/ui components.
- (decision) Use a Node.js and TypeScript local service as the orchestration and API boundary; keep browser code responsible for presentation and user interaction, not privileged filesystem access or heavy media processing.
- (decision) Use FFmpeg as the media demux/decode/encode boundary for MP3, WAV, M4A, FLAC, MP4, MOV, and MKV; preserve the original input and write processed outputs as separate files.
- (decision) Use ONNX Runtime Node.js for local AI inference behind a model adapter so CPU execution is always supported and hardware acceleration can be added when the platform supports it.
- (decision) Use npm-based setup as the lowest-friction cross-platform installation path; target the current Next.js-supported Node.js baseline of 20.9 or newer and verify the exact runtime in the installer.
- (direction) Use a single repository with a web application and local processing service separated by explicit API/job contracts; keep model adapters replaceable so speech-first processing can later expand to music and mixed audio.
- (version) Official documentation checked: Next.js supports macOS, Windows including WSL, and Linux with a minimum Node.js version of 20.9; Tailwind's current Next.js setup uses Tailwind CSS v4; shadcn/ui supports Next.js with React 19 and Tailwind v4; ONNX Runtime Node.js provides CPU binaries across Windows, Linux, and macOS x64/arm64, with platform-specific acceleration options.
- (question) The interaction model for file safety, preview, cancellation, and output naming remains to be confirmed before finalizing the UX and job-state invariants.
- (decision) Use Next.js server capabilities and Node.js as one local runtime rather than introducing a separate backend framework; Next.js route handlers/server actions may expose the local API, while a separate in-process or child-process job worker handles long-running media tasks.
- (decision) Never modify the original input. Every processing run creates a separate output artifact.
- (decision) The UI must provide before/after preview, independent effect toggles, per-effect intensity controls, output folder and filename selection, cancellation, retry, local history, and clear-history controls.
- (decision) Processing jobs must report explicit states and progress, validate output before marking success, and preserve diagnostic details for failed jobs without uploading user media.
- (direction) Add waveform or timeline preview, accessible keyboard-friendly controls, reduced-motion support, clear privacy messaging, disk-space checks, model/license attribution, and a first-run capability check for Node, FFmpeg, models, CPU/GPU acceleration, and writable storage.
- (direction) Treat pause/resume as capability-dependent: implement cancellation and safe retry in the first milestone; only expose pause/resume when the active pipeline can checkpoint safely without corrupting partial output.
- (constraint) All application state, job metadata, history, temporary files, model files, and outputs remain local to the laptop and are removable by the user.
- (assumption) A local browser tab cannot reliably choose arbitrary output paths on every supported operating system, so the local Next.js server will own file writes and the UI will provide a folder-selection mechanism appropriate to the local runtime, with a safe default output folder.
